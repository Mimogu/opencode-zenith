# OpenCode Harness Internals

Reference for working on `~/.config/opencode` itself. Not auto-loaded into sessions; `AGENTS.md` points here.

## Overview

```text
            daily 04:00 (opencode-benchmark.timer)
                       │
             model_lab.py ── graded tasks (lab_tasks.py) per provider budget
                       │ writes
                 ladders.json  ← one ranked chain per category
          ┌────────────┼──────────────┐
          ▼            ▼              ▼
   sentinel.py   auto-failover    router.sh
 (every 60 s:    plugin (in a     (manual one-shot)
  pick first     session: switch
  healthy model  on 429/5xx/cap/
  per category,  overflow)
  probe to move
  back up)
```

## Permission rule order

OpenCode v2 resolves the **last** matching rule. Rule 0 of every agent is the built-in `* * allow`.

- `opencode.json`: `shell * → allow` first, then the `ask` guardrails (`rm -rf *`, `sudo *`, `git push --force*`, ...). Appending a broad `allow` after them silently disables them.
- Do not add global `read * allow` or `edit * allow`: they override the built-in `.env → ask` and Plan mode's `edit → deny`.
- `agents/*.md` read-only sandboxes: `shell * → deny` MUST come first, then the allowlist. Deny-first produces allowlist semantics. Do not "tidy" it.
- Check effective rules with `opencode debug agents`.

## Model system

`ladders.json` holds the ranked chain for each category: `build`, `plan`, `explore`, `review`, `quick`. Nothing else hardcodes model lists. Agent frontmatter `model:` and `opencode.json:model/small_model` are written by the lab (ladder head) and the sentinel (first healthy model).

### Discovery (`model_lab.candidates`)

Each run scans `opencode models` and benches, per `settings.providers`:

| Provider | Pool | Daily budget (`settings.budgets`) |
|---|---|---|
| `opencode` | every `opencode/*-free` model | 14 messages (shared account-wide free allowance) |
| `openrouter` | every `openrouter/*:free` model | 20 |
| `omniroute` | models declared under `providers.omniroute.models` in `opencode.json` | 24 |
| `nvidia` | models declared under `providers.nvidia.models` in `opencode.json` (NVIDIA NIM free API, key `NVIDIA_API_KEY` in `free-models.env`; 40 req/min, 10,000 req/day per account, prompts logged by NVIDIA) | 60 |

Each provider is planned and spent separately, so benching gateways never touches the OpenCode allowance. Classifier/embedding/guard models are excluded (`NON_CHAT_RE`). To bench a new OmniRoute model, declare it in `opencode.json` first.

### Tasks and scoring

Graded tasks (`lab_tasks.py`, score 0..1 with partial credit) carry the ranking; each defeats a shortcut:

| Task | Measures | Shortcut it defeats | Cost |
|---|---|---|---|
| `code_multi` | fix 4 bugs from docstring spec, hidden checks, regression guards | editing the test (×0.5), fixing only what the visible test covers | 6 |
| `review_hunt` | find 3 defective lines among correct ones | flagging everything (false positives subtract) | 2 |
| `explore_trace` | trace a call through 6 files and an event registry | grepping for `open(` (a decoy writes the same file) | 4 |
| `plan_puzzle` | 2-worker scheduling optimum (14) | critical path (12), work/2 (13), greedy (16) | 1 |
| `instruction_multi` | three exact lines, sorted compact JSON | prose, labels, code fences | 1 |

Legacy pass/fail tasks: `code_fix`, `tool_use`, `context` stay in rotation; `sanity`, `instruction`, `reason`, `bug_hunt` saturate (every live model passes) and run only under `--full`/`--model`.

Per category, task weights × category multipliers (`WEIGHTS`, `CATEGORY_WEIGHTS`) give a 0..100 score. A task a model has not been given yet counts at the pool mean for that task, so rotation luck cannot decide rank; scores are then shrunk toward 50 by coverage.

**Data hygiene** (2026-11-04): `state/model_lab.db` held 114 rows for models that do not exist (`opencode/m0-free`…`m13-free`, all score 1.0, 104 of them dated up to 19 days in the future), left by a rotation simulation run against the real DB. Because a task a model was not given counts at the pool mean, they inflated every mean (`code_multi` ~0.83 where real models averaged 0.0), so an untested model outranked one that was tested and failed. They were deleted (backup of the DB before) and `latest_matrix` now ignores rows dated more than 1 h ahead. Run simulations against a copy (`oclib.LAB_DB`, as `tests/test_lab.py` does).

### Rotation (`plan_round`)

Per provider per day: up to 3 deep pairs, least-recently-measured first (planned before cheap probes so the 6-message task is never starved), then one cheap task for a rotating slice of 4 models. A pair is re-measured at most every 5 days; scores come from a 21-day rolling window. The offline test checks every (model, rotation task) pair is covered within the window.

### Ranking (`apply_ladders`)

One ranking across all providers per category: `score − latency penalty + settings.provider_bias[provider]` (default `opencode +8`, `omniroute 0`, `openrouter −2`). A free OpenCode model wins near-ties; a clearly better gateway model can lead. Unmeasured live models keep their previous order behind measured ones. To force the old "free tier always first" behaviour, set `provider_bias.opencode` to `100`.

### Failover and failback

- **In a session** (`plugins/auto-failover`): on 429/5xx/timeout/connection errors or context overflow the session switches to the next model in its category's chain and the failed model gets a ledger entry (60 s backoff, doubling to 15 min). The OpenCode free cap (`provider.free-limit`, or 429 on `opencode/*-free`) skips every free OpenCode model without a ledger entry. Plain 4xx bad requests do not fail over. A media-size rejection is not an overflow (see Image cap), and overflow compactions are limited to 2 per session per 10 minutes.
- **Across sessions** (`sentinel.py`, every 60 s): for each category, picks the first model with no ledger entry (and, while the free cap is on, not `opencode/*-free`), and writes it to that category's agents and the default/small model. A model with a ledger entry is probed once its backoff ends; a healthy probe clears the entry and the category moves back up. While capped, one probe per 15 min checks whether the free allowance is back. At most 3 probes per loop, 1 per model per 15 min. `"pin_model": true` in `opencode.json` freezes routing.

### Quota reality

The OpenCode free tier is one shared daily allowance, enforced server-side and invisible to the CLI: a capped run returns an empty response while `~/.local/share/opencode/log/opencode.log` records `Free usage limit reached`. `oclib.free_limit_since` reads that marker. The lab aborts only that provider's round on the first hit, so a quota wall is never recorded as a capability failure.

`opencode run` reads a non-TTY stdin to EOF before it starts, so callers must pass `stdin=DEVNULL` / `</dev/null` (an inherited open pipe hangs it until the timeout); `oclib.run_model` and `router.sh` do.

The CLI resolves a session's working directory from `$PWD`, not the process cwd. Any wrapper that runs `opencode` in another directory must set `PWD` in the child environment; `oclib.run_model` does.

Never hand-edit `ladders.json` while the timer is running; the lock serializes writes but the last writer wins. Settings (`providers`, `budgets`, `provider_bias`) live under `settings` in `ladders.json` and survive lab runs.

## Context engine (memory + skills)

`plugins/context-engine` runs on every model step (`session.hook("context")`) but decides once per user message; the result is cached for the turn, so the system prefix stays stable and provider prompt caches keep hitting. Measured in the long-running service: 55–85 ms per decision, of which the one query embedding is ~55 ms and everything else 2–20 ms; later steps of the turn ~0 ms.

```text
user message ─┬─ embed once (Ollama, cached LRU, shared by both below)
              ├─ skills.mjs  regex routes (skill-routes.json) + BM25 keywords over description,
              │                examples and learned prompts (must cover ≥80% of the prompt)
              │              + semantic: max cosine over description, generated examples
              │                (skill-examples.json) and learned prompts, minus the skill's
              │                baseline (hubness correction, skill-neutral-prompts.json)
              │              confident → injected as native <skill_content>; weaker → hint
              ├─ memory.mjs  facts + sessions: BM25 keywords + cosine (RRF)
              │              one gate: score ≥ floor AND ≥ best − gap (both calibrated);
              │              strong keyword coverage lowers the floor slightly
              │              → ≤4 facts + ≤2 past sessions as "# Recalled memory"
              ├─ playbooks   task checklist (playbooks.json) appended after the user's message
              ├─ prune.mjs   earlier turns: drop reasoning, dedupe repeated calls, trim stale output
              └─ catalog     <available_skills> descriptions abridged (~31k → ~12k chars per step)
```

- **Embedding model**: `"_active"` in `memory-calibration.json` is the single place the choice is recorded; plugin (`embed.mjs`) and engine (`lib/agy_recall.py`) both read it (`OPENCODE_EMBED_MODEL` overrides). Currently `embeddinggemma`, chosen with `tools/recall_eval.py` on 2026-11-03: hit@1 0.98 (nomic 0.96, qwen3-embedding 0.96, all-minilm 0.89), relevance margin 0.29 (nomic 0.16), ~57 ms/query; its QAT q8 build was 2× slower on this CPU. Vectors are stored with their model and only same-model vectors are used; the indexer re-embeds the rest. After changing `_active`, restart the sentinel and `opencode service restart` so no long-running process keeps the old model.
- **Ollama on demand**: `ollama.service` is not started at boot. The plugin starts it (`embed.ensureServer`, allowed without a password by `/etc/polkit-1/rules.d/50-ollama-ondemand.rules`); the model unloads 20 min after last use. Bench/sentinel runs do not start it (`OPENCODE_CONTEXT_ENGINE=0`). If Ollama is down recall degrades to keyword search; nothing blocks. Background document embedding yields to queries (Ollama serves one request at a time).
- **Thresholds**: never hand-tuned. `python3 tools/recall_eval.py <model> --write` measures 45 paraphrased questions with known answers, 25 negatives (including hard technical ones) and a 30/18 skill set, then writes floor, gap, duplicate/related cut-offs and skill cut-offs per model. `bun tools/recall_e2e.mjs -v` runs the same cases through the shipped plugin (2026-11-03: memory 92% answered, 83% of injected items relevant, 0 injections on negatives; skills 30/30, 1/18 false). Re-run both after adding many facts or changing the model; add a case to the eval when recall gets something wrong.
- **Writer**: `lib/agy_recall.py` (+ `lib/agy_memory_engine.py`, symlinked into `~/.local/lib` for `mem` and the MCP server). It embeds facts on write and, from the sentinel every 10 min (`oclib.refresh_memory_index`): indexes finished sessions into `episodes` (title + request + compaction summary; untitled/one-shot/probe sessions skipped; `redact()` strips credentials) and **extracts facts**. The plugin only reads (plus access counts).
- **Keywords** (`keywords.mjs`, Python twin `lib/agy_keywords.py`, shared `keyword-lexicon.json`; `tests/test_keywords.py` checks both tokenize identically): light stemmer (running→run, caches=cache, configured=configure), conversational filler as stop-words, short terms kept (ui, db, c++, super+tab), BM25 ranking, typo tolerance (retreival→retrieval), word families (configure~configuration), a small synonym table (weaker than the word itself). Every match reports `cover`, the share of the query's information it explains; that, not "any word matched", is what counts as evidence. In RAM, rebuilt only when the store changes; ~1–3 ms per search. Without embeddings recall falls back to it (cover ≥ 0.55 and near the best score: 2026-11-03, 58% of questions answered, 70% of items relevant, previously 0%). Thresholds: `kw_*` in `memory-calibration.json` (`_keyword` for keyword-only), `min_keyword_cover` in `skill-routes.json`; sweep with the `OPENCODE_KW_*` env vars and `tools/recall_e2e.mjs` (prefix `OLLAMA_HOST=127.0.0.1:9` for keyword-only).
- **Playbooks** (`playbooks.mjs`, `playbooks.json`): free models skip what a top model does unprompted (look before answering, confirm a command exists, reproduce a bug, re-run after a fix, search for facts that change). Per user message the engine picks up to 2 task checklists: `own-machine`, `fix-bug`, `change-code`, `research`. A playbook is picked by a regex route, or when it is the single most similar one and its similarity to the examples is at least `threshold` (0.34). The checklist and a one-line self-check (`always`) are appended to the user's message in the request only, never stored, because weak models follow instructions next to the request far better than ones in the system prompt. This applies only to the agents listed in `agents`; subagents get nothing. Measured 2026-11-03 on held-out prompts: 17/19 picked the right playbook, and 1/14 unrelated prompts got one. On `flint-40b-free`, the zram question went from generic advice with a wrong command to checking swap and zram and answering for the machine. Cost: ~150–250 tokens per matching turn. Tune with new examples or routes, not a lower threshold. `OPENCODE_NO_PLAYBOOKS=1` disables it. Since 2026-11-04 `research` also routes buying/price questions and requires stock and price to be read from the product page itself (an 8GB RAM run on `glm-5.3-flash-free` called an out-of-stock 799 EGP listing "in stock, verified today" when live stock was 3,350+ EGP), and `always` forbids "verified" for anything not read this session. 2026-11-04: two more playbooks, `browser-task` (act then look, done = final state seen, never type credentials) and `documents` (use the office skill, render to PNG with `pdftoppm` and look with `see`), `change-code` gained "look at anything visual" and "numbered steps for 3+ step work"; `skip` regexes (acknowledgements, memory requests) give no playbook, and a semantic pick needs ≥4 words. `bun tools/playbook_eval.mjs`: 23/23 prompts right, 0/8 unrelated prompts got one (was 13/18 before the tuning; "the wrong price" had picked the shopping checklist).
- **Fact extraction**: per finished session, oldest first, the gateway model (`omni-quick`, not the OpenCode free tier) reads the user's messages + summary and proposes ≤3 durable facts dated with the session date (no secrets, paths, config values or task details). Near-duplicates are skipped; a related fact goes to a one-word judge (UPDATE/DUPLICATE/DIFFERENT) and an UPDATE supersedes the older fact, keeping history. User-stated facts are never overwritten. Stored as `auto-extracted`, unverified, with `source_session` (shown by `mem`/`memory_search`; the gist is in `episodes`); recall labels them `auto <date>`. Facts of origin `user-statement` or `verified-fact` are never auto-superseded. 5 sessions per pass; `extraction_log` records each. Review with `mem` / `memory_audit`; fix with `memory_forget` / `memory_supersede`.
- **Link check** (`linkcheck.mjs`, every step, every agent incl. subagents): free models present URLs they never opened, or opened and got an error page, as verified (2026-11-04: the browser subagent typed an Amazon product ID, got 404, wrote "In stock, read on-page"; the parent made it the top pick). The engine (1) pins failures already in the session (webfetch errors, which reach plugins as `result: {type: "error", value: {error: {message}}}`, `HTTP Error 404`, "Page Not Found", challenge pages, timeouts) to their URL and re-opens each such URL once itself (Amazon answers 503 to webfetch but 404 for a product ID that does not exist), (2) opens each product link in a subagent's report (`subagent` tool result) once (GET, browser UA, 8 s, ≤12 per report; search pages, docs and comparison sites skipped) and (3) appends a `[harness link check` note to the tool result carrying the URL: `DOES NOT EXIST (HTTP 404)` or `could not be opened`. Verdicts are cached 30 min so later steps stay byte-identical; messages are cloned, never edited in place. On that run's 6 links: both invented IDs → dead, 4 real pages → ok, 1.6 s. Playbooks also apply to the `browser` and `general` subagents now. Off: `OPENCODE_NO_LINKCHECK=1`. Test: `bun test tests/linkcheck.test.mjs`.
- **Answer check** (`answercheck.mjs`, hook `experimental.idle`, the same hook + `api.session.synthetic` that OpenCode's own `/goal` uses): when a top-level `build`/`quick`/`plan`/`local` turn ends, the final answer is checked mechanically and, if wrong, the agent is sent back once with a `<system-reminder>` naming the problem: (1) every shop/product URL in the answer is opened (dead → "does not exist (HTTP 404)"), (2) "tests pass / build succeeds / type checks pass" with no test, build or type-check command in the turn (shell, `execute`, or a subagent report). One round per user message (in-memory key + the stored `synthetic` row with `metadata.source = "answer-check"`); subagents and turns with background shells still running are skipped (`background` is the list of running shells, so `[]` means idle). It reads the turn from OpenCode's DB read-only (`session_message`: `user` → `assistant` with `tool` parts → `synthetic` → `idle`). Measured 2026-11-04 on a private server: a formatted answer with an invented Amazon link was sent back and the agent replied "Corrected: item one was a dead link (404)…" with the real listing; the next idle logged "already checked"; a real bug fix with `python3 -m unittest` logged "ok". Off: `OPENCODE_NO_ANSWER_CHECK=1`; skip reasons: `OPENCODE_ANSWER_CHECK_DEBUG=1`. Test: `bun test tests/answercheck.test.mjs`.
- **Tool hints** (`toolhints.mjs`, every step): a failed tool call gets one line saying what works instead, appended to the error itself (cloned, byte-stable): search HTTP 429 → use `tools.parallel.web_search` (a separate provider; only real 429s, not results that mention rate limits); webfetch 403/429/503/timeout on bot-walled shops (Amazon, Jumia, Noon…) → `browse` or the `browser` subagent; other webfetch 5xx/timeouts → retry once, then `browse`; shell `command not found` → `command -v`/`pacman -F`, do not guess. Off: `OPENCODE_NO_HINTS=1`.
- **Write rules** (`check_write` in `lib/agy_memory_engine.py`, used by `memory_mcp.py` and `mem`): `memory_add`/`memory_supersede` and `mem add`/`mem supersede` require `origin` (`user-statement` | `verified-fact`) and `evidence` (the user's quoted words, or the command/file/URL that showed it); the evidence goes to `audit_log`. Writes mentioning prices, currency amounts, stock or "recommended purchase" are refused, and extraction drops them too (`VOLATILE_RE`). Before this, `memory_add` defaulted to `user-statement`, so an agent's own wrong recommendation was stored as something the user said and protected from auto-supersede. Extraction also skips devices/accounts named only in a pasted brief (an HP laptop belonging to a friend became "the user owns an HP"). Full audit of all 43 facts on 2026-11-04: 6 removed (wrong, duplicate or inferred), 8 corrected.
- **Skills**: `tools/skill_examples.py` (re)generates 6 example requests per skill when a description changes. When the agent loads a skill the router did not inject, that prompt is saved to `state/skill-learned.json` (≤8 per skill) and matched next time. At most 2 injected skills, ≤ 48k chars of bodies per turn; larger skills are hinted. Short follow-ups keep the previous turn's skills for 2 turns. Curated regex routes stay authoritative; fix misses and false positives there.
- **Pruning** (`prune.mjs`, request view only; nothing stored changes and everything shortened can be re-run or re-read): (1) superseded notices: OpenCode re-announces the full Code Mode tool catalog whenever an MCP server connects (lazily, 4–10 s each) and the full skill list when skills change, each saying it supersedes the last; older copies are dropped (one session carried 41 = ~72k tokens), and the system prompt's own catalog becomes a one-line pointer once a newer one exists. Instruction diffs and "new skills" additions are incremental and kept. (2) earlier turns: reasoning dropped, repeated identical calls collapsed to the newest result. (3) the turn in progress, which is most of a long session: the last 10 steps are untouched; older ones get shortened reasoning (signed Anthropic reasoning is never touched), long shell/web/MCP output cut to head + tail, reads of files changed or re-read later replaced by a marker, other long reads head + tail, earlier `write` contents and long edit strings replaced by a marker. The aged boundary moves only every 8 steps, so the request prefix stays byte-identical in between and prompt caches keep hitting. Replaying 546 real sessions (`bun tools/prune_report.mjs`, 2026-11-03): history re-sent −47% (old pruner −22%). `OPENCODE_NO_PRUNE=1` disables it; `OPENCODE_PRUNE_KEEP`/`OPENCODE_PRUNE_CHUNK` exist only to exercise it in tests.
- **Progress notes** (`progress.mjs`, every step, top-level agents only; subagents are skipped by their "You are a subagent spawned…" opening): the user follows a task through the short messages between tool calls. Measured 2026-11-13 on real sessions: final replies already followed AGENTS.md, but updates either narrated ("Let me check… Now let me read…") or stopped for 7–11 calls. The engine appends a `[harness progress note` to a tool result (1) on the 5th, 10th… step in a row with no message to the user (parallel calls in one step count once) and (2) after two announcement-only updates in a row (first sentence "Let me…", "Now I'll…"; the turn's opening plan does not count), asking for 1–2 sentences that lead with the finding. Notes depend only on the conversation up to that result, so earlier steps keep identical bytes. Replay on 5 real sessions: 0–4 notes per long turn, none on short ones. AGENTS.md "While working" has the matching wording. Off: `OPENCODE_NO_PROGRESS=1`. Test: `bun test tests/progress.test.mjs`. (`bun` = the npm one in `~/.npm-global`, repaired 2026-11-17; OpenCode's own runtime also works: `BUN_BE_BUN=1 /usr/lib/opencode-desktop/opencode-cli test …`.)
- **Image cap** (`media.mjs`, every step, every agent, and the `compaction` hook; request view only): every image an agent reads (page renders, screenshots) stays in the conversation as base64 and is re-sent on every step. 2026-11-10, "20+ page Word report" on `inkling-2-small-free`: after 64 page images (9.2 MB of base64 in the session) the provider answered 400 `[airlock_error] inlined media exceeds the 33554432 byte total limit` on every step and on every compaction (the compaction request carried the same images), and `auto-failover` read "exceeds … limit" as a context overflow and called `session.compact` every ~7 s for 30 minutes. Now: (1) once the inlined images pass 4 MB of base64 or 24 images, the oldest are replaced by a one-line note (file name, size, "read the file again if you need another look") until 2 MB / 12 remain; the newest is always kept, a single image over the budget gets advice to use `see` or a smaller copy; the cut is replayed from the start of the conversation, so it moves only when the budget is passed again and the prompt-cache prefix stays identical in between. (2) compaction, title and summary requests carry no images. (3) `auto-failover` treats a media-size rejection (`MEDIA_LIMIT`) as its own case: `tighten(sessionID)` halves that session's image budget and the step is retried, up to 4 times (then nothing is attached; then the request stops). (4) `mayCompact`: at most 2 failover compactions per session in 10 minutes, after that the error goes down the normal failover path. Measured on a copy of the real session (private server, copied DB): compaction completed (was 20 failures), and a forked step on the same model answered with 12 of the 64 images attached (request 2.1 MB). The stored size that tripped the provider's 32 MB limit was only ~9 MB, so its count is roughly 3.7x ours: keep the budget well under 8 MB. Log lines: `media:` in `context-engine.log`, `media limit` in `failover.log`. Off: `OPENCODE_NO_MEDIA_CAP=1`; budget: `OPENCODE_MEDIA_HIGH`/`_LOW` (bytes), `OPENCODE_MEDIA_HIGH_COUNT`/`_LOW_COUNT`. Test: `bun test tests/media.test.mjs`. To test against a real session without touching it: `sqlite3 -readonly opencode.db ".backup <dir>/opencode/opencode.db"`, symlink the other entries of `~/.local/share/opencode` next to it, `XDG_DATA_HOME=<dir> opencode serve --port 4599`, then `opencode run --server … -s <id> --fork` or `opencode api POST /api/session/<id>/compact -d '{}'`.
- **Fixed prompt**: the skill catalog is sent as one line per skill (`- id: first sentence`), all skills kept (14.2k → 7.6k chars per step); agent descriptions say only when to use the agent (the method lives in the agent body) because they are repeated in the `subagent` tool on every step. Measure with `OPENCODE_CONTEXT_DUMP=<file> opencode run --standalone "…"` (sizes of the system blocks, tools and messages actually sent; `OPENCODE_CONTEXT_DUMP_FULL=1` adds the text). 2026-11-03: system prompt ~38k → 24–29k chars, a 5-step request ~98k → ~60k.

## Browsers

MCP server binaries are installed from `mcp-servers/package.json` (pinned, `cd mcp-servers && npm ci`; `node_modules` is gitignored) and started directly: 0.2–0.7 s each instead of ~2.2 s through `npx -y`, and no npm registry or `npm notice` noise at start. Real browser automation (the default for user web tasks): `browse` (OpenCode Browse extension MCP on relay `127.0.0.1:19988`, drives the user's active browser preserving logins and tab groups with CAPTCHA handoff), and `chrome-devtools` (traces, Core Web Vitals, network/console, memory). Artifacts: `/var/tmp/pip-scratch/opencode/browser/`. Code Mode does not list MCP tools in the system prompt (the model discovers them via `search`), so extra servers cost ~0 tokens per step. The `browser` subagent exists to keep long web tasks out of the main context, not to gate tools. Versions are pinned; bump only to releases at least two weeks old.

**The user's own browsers.** Nothing is hardcoded. `bin/browser-ctl` (symlinked in `~/.local/bin`) reads the desktop entries with `Categories=WebBrowser` (XDG dirs, `~/.local`, Flatpak exports) on every call and detects each engine from the browser's own `--version` (cached per desktop file + mtime in `state/browsers.json`), so installing or removing a browser changes the list at once. `list [--json]`, `status [id]`, `start id [url]`, `restart id` (only after the user agreed; tabs restore), `stop id`, `match "text"`. Exit 3 = open without its automation port, 4 = another browser holds the port, 5 = cannot be automated (desktop-control instead).

| Engine | Port | MCP |
|---|---|---|
| Chromium family (Brave, Chrome, Chromium, Opera, Helium, Vivaldi, Edge...) | Browse relay 127.0.0.1:19988 | `browse` (OpenCode Browse extension) |
| Firefox family | Marionette 2828 + WebDriver BiDi 9223 | `my-firefox` (`@mozilla/firefox-devtools-mcp@0.10.6 --connect-existing`) |
| qtwebengine (qutebrowser) | CDP 9222 via `--qt-flag` (experimental) | `my-browser` |
| a Windows app over RDP (WinApps) / unknown | none | desktop-control skill |

Gotchas, all handled by `browser-ctl`: Google Chrome 136+ refuses remote debugging on its main profile ("requires a non-default data directory"); `start` sees that in the log and relaunches with a separate automation profile (`~/.var/app/<flatpak-id>/data/opencode-automation-profile` or `~/.local/share/opencode/browser-profiles/<id>`) that starts signed out. Flatpak processes are found with `flatpak ps` child PIDs and their descendants; SIGTERM goes to the browser's main process (no `--type=`), not the sandbox wrapper. Chromium closed from outside its UI marks the profile `exit_type=Crashed` ("Restore pages?" next time): `stop` reads the open profile dirs from `/proc/<pid>/fd` before closing and resets them to `Normal`; `start` passes `--hide-crash-restore-bubble`. Firefox needs `--remote-debugging-port` as well as `--marionette`, and its default port 9222 would collide with CDP, hence 9223. The ports are bound to 127.0.0.1 and opened only on demand: while open, any local process can control that profile.

**Which browser a request uses** (`plugins/context-engine/browsers.mjs`, per user message, list from `browser-ctl list --json --no-state`, cached 60 s): a browser the user names (aliases from the desktop entry name; "chrome devtools"/"firefox extension" do not count) → a reminder next to the request says to `browser-ctl start <id>` and use its MCP; the user wants their own/a real browser driven but names none ("use my browser", "automate the browser", "take over the browser") → a reminder says to ask with the question tool, listing what is installed plus "built-in headless"; anything else → nothing added, the headless servers stay default. `OPENCODE_NO_BROWSER_INTENT=1` disables it.

## Verified replies (`plugins/verify-claims`)

An agent may not report a change it did not make, nor "Done" on work that is not shown working. On `experimental.idle` (the agent has given its final reply) the plugin reads the turn with `api.session.context()` and, when needed, sends the agent back with `api.session.synthetic()` (the same mechanism as OpenCode's goal feature; `opencode run` waits for it). At most 2 rounds per user message.

1. **Deterministic check**: claim lines in the reply ("I edited…", "- Edited `~/x`", "1. **Restarted** …", "## What I changed" bullets, "Fixed:"; negations and suggestions excluded) against the turn's evidence: successful edit/write/patch calls and paths, shell commands that can change something (redirects, `sed -i`, `tee`, mv/cp/rm, `systemctl restart`, package installs…, exit 0), and the mtime of every file the reply names. No change behind a claim, or a named file not modified this turn → nudge with the specifics. Recap questions ("what did you change?") are judged against the whole session.
2. **Outcome + accuracy review**: a fix/change request whose reply says Done/Fixed/"is now configured", or any reply of 400+ chars after tool use, goes to a gateway reviewer (lab-ranked by review score, ties to review/reasoning models; `omni-review` today) with the request, every tool call + output and the reply. It lists each factual claim of the final reply with a quote from a tool output, or `none`. `continue` (work not done) → nudge with its reason and an on-machine next step (the reviewer is told not to prescribe from memory: versions change); `revise` (work fine, some claim without evidence, e.g. an earlier "almost certainly" guess stated as fact) → nudge to verify or drop just those sentences. On run 4's real session it flagged exactly the invented "(quoting issue)" history and passed the same reply with that sentence removed. Cost: one reviewer call (~5–15 s, transcript ≤ 60k chars) per reviewed turn. **Reviewer model** is measured, not configured: `bun tools/reviewer_eval.mjs` runs every gateway model that answers (a 1-call probe skips dead ones: 19 of 231 on 2026-11-05) on `state/reviewer-cases/*.json` (real session turns with the right verdict: invented history, a self-contradicting swap report, a restarts-only "fix", their corrected versions, a good fix) and writes `state/reviewer-ranking.json`; models scoring ≥ 0.8 are used best first, re-measured in the background when a week old; `--show` prints it. 2026-11-05: `omni-code` 6/6 (7.6 s), `agy/claude-opus-4-6-thinking` 6/6 (50 s), `omni-review` 5/6, `gemini-3.8-flash-tiered` 5/6, `auto/*` routers ≤ 4/6. ### Any browser: generated tool sheets and one method (2026-11-18)

## graphify MCP

System unit `graphify-mcp.service` with drop-in `stateless.conf` (`--stateless`): OpenCode's background service keeps one long-lived MCP session, and the default 1 h idle reaper used to kill it, after which every reconnect failed with 404 until OpenCode restarted.

## RTK (shell output compression)

`plugins/rtk.ts` (written by `rtk init -g --opencode`, RTK 1.1.0 in `~/.local/bin/rtk`) rewrites shell commands to `rtk <cmd>` via `execute.before`, so outputs reach the model condensed. It asks `rtk hook opencode` per command and keeps the command as typed whenever the rewrite would change what the permission rules decide (the `ask` guardrails still prompt). Agents whose frontmatter declares `permissions:` (the read-only sandboxes) are not rewritten. Savings: `rtk gain`. Unfiltered once: `rtk bypass <cmd>`. Off for a session: `RTK_DISABLED=1`. Upgrade: download the release + `checksums.txt` from github.com/rtk-ai/rtk, verify SHA-256, `install -m 755`.

## Skills from Claude Code

OpenCode also scans `~/.claude/skills` (Claude Code compatibility). The skills synced there from claude.ai (`computer-use`, `chrome-browser`, `built-in-browser`, `google-workspace`, `docs`, `import-memory`, `morning`) are proprietary Anthropic materials licensed only for use inside Anthropic's services, and they call tools OpenCode does not have. Keep `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` in the environment that starts OpenCode; `oclib.run_model` sets it for lab and sentinel runs.

OpenCode has its own equivalents, written for its tools: `browser-automation` (playwright + camofox MCP), `desktop-control` (`desk.sh`: grim, tesseract, ydotool, wtype on labwc) and `memory-import` (memory MCP). They are excluded from the Claude Code sync because Claude Code has the originals.

## Web search

The built-in `websearch` tool uses `"websearch": {"provider": "exa"}` in `opencode.json`. The OpenCode account layer (first source in `opencode debug config`) sets `provider: "opencode"`, a paid search that failed with HTTP 402/503; `random` does not move off a provider on 402. Check with `opencode api POST /api/websearch -d '{"query":"test"}'` (`providerID` in the reply). Keyless Exa, Parallel and Firecrawl answered on 2026-11-04; TinyFish needs a key (401).

Fallback: keyless Exa rate-limits under heavy use (a browser subagent got HTTP 429 16 times in one run, 2026-11-04) and the built-in tool has no fallback on a pinned provider, so the `parallel` remote MCP (`https://search.parallel.ai/mcp`, keyless: `web_search` with `objective` + `search_queries`, `web_fetch`) is configured too. AGENTS.md names it, and a 429 search error carries a hint pointing to it (Tool hints).

## Long tasks: `/goal`

OpenCode v2 has a built-in `/goal <objective>` command ("keep working until an objective is met", `pause|resume|clear`): at every idle a goal reviewer model answers done / continue / wait, and on "continue" the session is resumed with the next step, until done, a round limit or no progress. Use it for multi-step work that should not stop after one answer. The answer check above runs on the same hook and does not interfere (one round per user message).

## Updates

The CLI comes from `opencode-desktop-bin` (chaotic-aur), so the built-in updater is disabled — `"update": "notify"` only. Upgrade through pacman:

```bash
yay -Syu opencode-desktop-bin     # or: sudo pacman -Syu
```

`model_lab.py` logs a warning when `yay -Qu opencode-desktop-bin` reports a new version.

## Stack lifecycle (on demand)

`omniroute`, `opencode-sentinel` and `camofox-browser` are no longer started at login. `~/.local/bin/opencode-stack` runs them only while OpenCode is open (added 2026-11-07, to free ~1 GB of RAM for games):
- `~/.local/bin/opencode` (wrapper, was a symlink) and `~/.local/bin/opencode-desktop` (used by the `.desktop` overrides in `~/.local/share/applications`) run `opencode-stack up` before starting OpenCode.
- `opencode-stack-watch.service` stops the units and the background server (`opencode service stop`) 45 s after the last client closes (`OPENCODE_STACK_GRACE`). Clients: the desktop app and any `opencode-cli` process that is not `serve` and not inside the stack's own units.
- `opencode-benchmark.service` has drop-in `stack.conf` (`Wants=` the three units), and the watcher keeps the stack up while the bench runs.
- Manual: `opencode-stack up | down | status`. If `oc-status.py` shows the services inactive while no OpenCode is open, that is expected.
- Shell sidebar (added 2026-11-13): the end4-pC AI sidebar's OmniRoute models (`omni-code`, `omni-review`, `omni-quick`, `omni-explore` in `~/.config/illogical-impulse/config.json` `ai.extraModels`) source `~/.config/hypr/custom/scripts/omniroute-sidebar.sh` before each request. It starts only `omniroute.service` if it is down and touches `/run/user/$UID/omniroute-sidebar.lease`; while that lease is younger than 10 min (`OPENCODE_STACK_SIDEBAR_LEASE`), an idle watcher keeps omniroute and stops only sentinel, camofox and the background server.
